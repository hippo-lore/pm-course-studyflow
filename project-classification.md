# Класифікація проєкту та аналіз оточення (StudyFlow)

## 5.1. Класифікація проєкту

| Ознака класифікації | Обрана категорія | Обґрунтування |
| :--- | :--- | :--- |
| **Розмір проєкту** | Малий | Проєкт виконується невеликою командлю здобувачів освіти протягом одного навчального семестру із чітко обмеженим функціоналом. |
| **Тип продукту** | Веб-застосунок | Продукт розробляється як веб-платформа, доступна через браузер, що забезпечує швидкий доступ користувачів без необхідності встановлення додаткового ПЗ. |
| **Галузь застосування** | Освіта (EdTech) | Основне призначення системи — оптимізація навчального процесу, тайм-менеджменту та організації освітніх матеріалів для студентів і викладачів. |
| **Рівень невизначеності вимог** | Середній | Основне бачення та базовий функціонал визначені на початковому етапі, проте детальні детальне уточнення вимог відбуватиметься під час ітеративної розробки та збору зворотного зв'язку. |
| **Модель співпраці** | Внутрішній продукт / навчальний проєкт | Проєкт розробляється всередині команди в межах навчальної дисципліни з управління IT-проєктами для демонстрації практичних навичок та тестування на навчальній аудиторії. |
| **Тип життєвого циклу** | Гнучкий (Agile / Scrum) | Використовується ітеративний підхід із розбиттям роботи на спринти, що дозволяє гнучко реагувати на зміни вимог та поступово нарощувати функціонал продукту. |

## 5.2. Аналіз внутрішнього оточення

Чинники внутрішнього середовища проєкту StudyFlow, що впливають на його виконання:

* **Склад і компетенції команди:** Команда складається зі студентів, які поєднують ролі проектного менеджера, frontend/backend розробників та QA. Наявний базовий рівень володіння сучасними веб-технологіями та інструментами командної розробки.
* **Наявні технічні ресурси:** Розробка здійснюється із використанням безкоштовного інструментарію (GitHub для версіонування коду та управління завданнями, сервіси Vercel/Render для деплою, локальні середовища розробки IDE).
* **Часовий бюджет команди:** Кожен учасник команди має можливість виділяти близько 6–10 годин на тиждень для роботи над проєктом, поєднуючи розробку з іншими навчальними дисциплінами.
* **Досвід учасників з обраною тематикою:** Учасники команди є безпосередніми представниками цільової аудиторії (студентами), що надає глибоке розуміння проблематики та потреб користувачів без додаткових досліджень.
* **Організаційне середовище:** Проєкт реалізується в університетському середовищі з чіткими дедлайнами контрольних точок (лабораторних робіт), вимогами до документації та оцінюванням результатів викладачем.

## 5.3. Аналіз зовнішнього оточення

Чинники зовнішнього середовища, які впливають на проєкт:

* **Цільова аудиторія та її потреби:** Студенти, викладачі та самостійні здобувачі освіти. Основні потреби: зручний розклад, трекінг виконання завдань, централізоване збереження навчальних матеріалів та нагадування про дедлайни.
* **Наявні аналоги і конкуренти:**
  1. *Notion* — потужний інструмент для ведення нотаток та баз даних. Перевага: гнучкість; недолік: високий поріг входження для студентів та відсутність спеціалізованого освітнього шаблону «з коробки».
  2. *Google Classroom* — стандартна платформа для навчальних закладів. Перевага: інтеграція з Google Workspace; недолік: обмежений функціонал для персонального тайм-менеджменту студента.
* **Технологічні тренди:** Зростання популярності Single Page Applications (SPA), використання Progressive Web Apps (PWA) для мобільної адаптивності, застосування штучного інтелекту для генерації розкладів та персоналізації навчання.
* **Регуляторні або правові чинники:** Необхідність дотримання вимог щодо захисту персональних даних користувачів (GDPR, Законодавство України «Про захист персональних даних»), запезпечення безпеки збереження паролів та електронних адрес.
* **Партнерські системи або API:** Залежність від зовнішніх сервісів, таких як Google Calendar API (для синхронізації розкладу), REST API авторизації (OAuth 2.0 / Google Auth).

## 5.4. Обмеження та припущення проєкту

### Обмеження проєкту

| № | Обмеження | Категорія |
| :-: | :--- | :--- |
| 1 | Рералізація проєкту має бути завершена суворо до кінця навчального семестру. | Час |
| 2 | Відсутність фінансового бюджету на платні API, хостинг чи маркетинг. | Ресурси |
| 3 | Розробка має здійснюватися виключно із використанням веб-технологій (JS/TS, React/Node.js). | Технології |
| 4 | Обмеженість робочого часу учасників команди (до 10 год/тиждень на особу). | Ресурси |

### Припущення проєкту

| № | Припущення | Обґрунтування |
| :-: | :--- | :--- |
| 1 | Безкоштовні тарифи хостинг-провайдерів (Vercel/Render/Supabase) забезпечать достатню продуктивність для демонстрації продукту. | Для тестової аудиторії та перевірки викладачем лімітів безкоштовних планів буде достатньо. |
| 2 | Зовнішні API (Google Calendar, Auth) працюватимуть без збоїв та змін у документації протягом семестру. | Використовуються стабільні public API із довготривалою підтримкою. |
| 3 | Склад команди залишиться незмінним протягом всього періоду виконання проєкту. | Учасники зареєстровані в одній навчальній групі та зацікавлені в успішній здачі дисципліни. |
| 4 | Студентська аудиторія готова тестувати веб-застосунок та надавати зворотний зв'язок. | Наявність доступу до одногрупників та студентської спільноти. |

## 5.5. Висновки

Обрана класифікація (малий веб-проєкт із середнім рівнем невизначеності вимог) безпосередньо зумовлює доцільність використання гнучкої методології управління Agile (Scrum/Kanban). Оскільки розробка є навчальним проєктом із фіксованими часовими рамками, використання коротких ітерацій (спринтів) дозволить регулярно демонструвати працюючий функціонал та адаптувати пріоритети завдань під вимоги викладача.

Найкритичнішими чинниками оточення для успіху проєкту є внутрішні обмеження часу команди та її технічні компетенції, а також зовнішня залежність від безкоштовних сервісів розгортання та партнерських API. Оскільки команда поєднує розробку з іншими предметами, ризик неефективного розподілу часу є найвищим.

Виходячи з проведеного аналізу, на даному етапі можна виділити такі ключові ризики: ризик виходу за межі дедлайнів через брак часу, ризик технічних блокувань при інтеграції сторонніх API та ризик ускладнення інтерфейсу для кінцевого користувача. 

З урахуванням виявлених факторів, подальшими кроками команди є: декомпозиція вимог до продукту на зрозумілий бэклог (Backlog), чіткий розподіл завдань між учасниками з урахуванням їхніх компетенцій, а також налаштування базової інфраструктури розробки (CI/CD) та створення прототипу інтерфейсу.

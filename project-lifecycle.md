# Життєвий цикл проєкту (StudyFlow)

## 5.1. Обрана модель життєвого циклу
* **Конкретна модель:** Scrum (як представник гнучких/адаптивних моделей).
* **Тип моделі за сучасною класифікацією:** Адаптивна / Гнучка (Adaptive / Agile).
* **Обґрунтування вибору:** Вибір моделі Scrum зумовлений результатами класифікації проєкту (Лабораторна робота №2), зокрема середнім рівнем невизначеності вимог до веб-застосунку та розробкою в умовах обмеженого студентського часу. Оскільки користувацький досвід та деталі функціоналу платформи StudyFlow уточнюватимуться ітеративно під час тестування цільовою аудиторією, адаптивний підхід дозволяє гнучко коригувати пріоритети завдань. Розбиття процесу розробки на короткі спринти забезпечує постійний контроль якості та своєчасне постачання робочих інкрементів продукту.

| Ворота | Між фазами | Критерії переходу | Можливі рішення |
| :---: | :--- | :--- | :--- |
| **G1** | Фаза 1 (Концептуальна) → Фаза 2 (Розробка) | Успішно затверджено концепцію проєкту, оформлено основні документи (Brief, Classification, Lifecycle) у репозиторії. | Go / Rework / Kill |
| **G2** | Фаза 2 (Розробка) → Фаза 3 (Спринт 1) | Затверджено архітектуру, готові макети інтерфейсу та сформовано пріоритезований беклог задач. | Go / Rework / Kill |
| **G3** | Фаза 3 (Спринт 1) → Фаза 4 (Спринт 2) | Успішно реалізовано та протестовано базовий функціонал авторизації та розкладу (виконано цілі спринту). | Go / Rework / Kill |
| **G4** | Фаза 4 (Спринт 2) → Фаза 5 (Завершення) | Проведено повну інтеграцію модулів, створено робочу версію застосунку для фінального тестування. | Go / Rework / Kill |

## 5.5. Обґрунтування вибору моделі
Вибір адаптивної моделі (Scrum) для проєкту StudyFlow безпосередньо спирається на результати попереднього аналізу, зокрема на середній рівень невизначеності вимог та необхідність швидкого реагування на змінні потреби студентської аудиторії. Оскільки розробка ведеться в умовах жорсткого обмеження часу та паралельного навчання учасників команди, класичні каскадні моделі (Waterfall) виявилися б неефективними через неможливість внести зміни на пізніх етапах без критичних втрат часу.

Альтернативні моделі, такі як класичний Waterfall або V-подібна модель, розглядалися на початковому етапі, але були відхилені через їхню жорсткість. Спіральна модель також розглядалася через глибокий аналіз ризиків, проте вона є занадто громіздкою та бюрократичною для невеликого студентського навчального проєкту. Натомість обрана адаптивна модель забезпечує баланс між чітким плануванням за допомогою фаз і воріт та гнучкістю під час самої ітеративної розробки.

Головними перевагами обраної моделі для StudyFlow є висока прозорість процесу, можливість регулярного отримання проміжних результатів (інкрементів) і швидке виявлення помилок ще на етапі спринтів. Завдяки цьому команда може вчасно демонструвати прогрес і коригувати функціонал.

Потенційними ризиками використання цієї моделі є розмивання обсягу робіт (scope creep) через постійне додавання нових ідей та ризик недотримання часових рам спринтів через завантаженість учасників на інших предметах. Для мінімізації цих ризиків команда використовує суворий облік завдань у беклозі, чіткі критерії завершення кожної ітерації (Definition of Done) та фіксовану тривалість фаз.
